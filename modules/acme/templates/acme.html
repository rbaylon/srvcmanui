A public DNS A record is required

Let's Encrypt proves you control this name by connecting back to this gateway over the public internet. Before you enable this or request a certificate, make sure an A record for the FQDN below points at this gateway's public IP address, and that inbound port 80 reaches it.

If that record is missing or points elsewhere, the request fails: the challenge never completes, no certificate is issued, and the existing one stays in place. Note that failed and repeated requests count against Let's Encrypt's rate limits, so fix DNS first rather than retrying.

The name the certificate is issued for, e.g. gw.example.com. At least two labels, letters/digits/hyphens only - it has to resolve publicly to this gateway.
While this is off, no certificate is requested and the web server is left alone. Turning it off does not put the self-signed certificate back - it only stops further requests.
Requesting a certificate installs /etc/acme-client.conf, runs acme-client for the name above, sets relayd.conf's TLS keypair to that name (keeping a timestamped backup of the original), then restarts relayd. The certificate is written to /etc/ssl/<fqdn>.crt and the key to /etc/ssl/private/<fqdn>.key, which is where relayd looks for the keypair it is told to use.
If relayd rejects the updated config, the previous one is restored and relayd is left running untouched - it serves this page, so a config it cannot load would lock you out.
