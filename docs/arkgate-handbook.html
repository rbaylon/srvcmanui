Running an ISP with Specz ISP

Specz ISP is an open-source control panel for small and mid-size Internet Service Providers — the kind of operator running their own OpenBSD router with pf, handing out DHCP leases, billing subscribers by the month, and needing one screen where all of that is a form instead of a config file.

Everything in Specz ISP revolves around one idea: a Router record (internally called a Pfconfig) stands for one physical or virtual OpenBSD box you operate. Nearly every form you'll meet in this handbook — interfaces, firewall rules, subscribers, DHCP scopes — asks which Router it belongs to, because Specz ISP can manage more than one node from a single dashboard. Throughout this handbook we'll follow one example deployment so the screens have something real to show:

Running example A wireless ISP called Example Net operates one edge router, Node1. Its WAN is em0 (gateway 203.0.113.1); its LAN is em1 (10.0.0.1/24). A subscriber, Grace Tan, is on the Home 50 plan at 10.0.0.50.

Signing in

Specz ISP has no public sign-up — an administrator creates your account (see Users) and hands you a username and password. Open the site, enter both, and you land on the Dashboard: system info, subscriber-to-plan and subscriber-to-gateway charts, live per-interface traffic, and gateway health.

How every form works

Specz ISP's forms are plain and consistent on purpose — once you've filled in one, you've basically learned all of them. A few patterns repeat everywhere:

  • Router — a drop-down naming which of your OpenBSD nodes this record belongs to. Skip it and Specz ISP has nowhere to file the record.
  • Letters/numbers-only fields — names, codes, and device identifiers reject spaces and punctuation on purpose; these values often end up written into a generated config file, where stray characters would break parsing.
  • IP address fields — accept a plain IPv4 or IPv6 address; leave them blank where a field's helper text says that's allowed.
  • Interface pickers — most Network and Services forms ask for an interface (em0, vlan10 …). That list is read live from whatever you've configured under Network Interfaces, so set those up first.

Saving vs. applying

This is the one behavior that trips people up, so it gets its own diagram: clicking Submit on any form saves your change to Specz ISP immediately, but it does not touch the router yet. Every save is queued as a pending change. A banner reading changes pending appears at the top of every page until you press Apply Changes there — that's the moment Specz ISP actually regenerates pf.conf, dhcpd.conf, unbound.conf, and reloads the affected services on the router.

Why this matters If a subscriber says their new plan speed "isn't working," the fix is almost always the same: someone forgot to click Apply Changes after saving.

Walkthrough: sign up a new subscriber

  1. Create their Plan first if it doesn't exist yet.
  2. Open Internet Provider → Subscribers → New.
  3. Fill in their name, address, and (if they have one) a static IP.
  4. Pick the Plan and leave Status as active.
  5. Submit, then don't forget Apply Changes.

Security

Access Policy /ui/policies

Specz ISP's own permission system — not pf's. A Policy grants one or more Groups either read-only or read-write access to one API resource. This is what decides what a non-admin User can see and touch inside Specz ISP itself.

Fields

FieldWhat it meansExample
Policy NamerequiredUnique, internal, letters/numbers only.SupportViewSubs
ModuleWhich Specz ISP module this policy governs.subs
Resourceany, or one exact API path this policy covers.any
PermissionRO read-only, or RW read-write.RO
GroupsWhich groups this policy applies to — check every group that should get this access.support
Careful A Resource of any grants that permission across the entire module, not just one record — reach for any for broad roles, and a specific path only when you mean to scope access to one exact record.

Groups /ui/groups

The simplest form in Specz ISP on purpose: a Group is just a name. Its only job is to be something both a User and an Access Policy can point at — the two combine to decide what that user can actually do.

Fields

FieldWhat it meansExample
Group NamerequiredLetters/numbers only.support
Tip Create the Group first, then attach an Access Policy to it, then add Users to it — in that order, a new hire's access is ready the moment their account is created.
